# Multi-store orchestration

Start from the verified local core with the dedicated `.local/kubeconfig` and `.tools/bin`. Never reset a cluster, PVC or database to repair a failed operation. `scripts/stores-deploy.sh` runs the frozen checks, creates only the new provisioner credential without rotating existing values, builds pinned platform/controller images, imports them into the existing owned cluster and upgrades the same platform Helm chart. Existing generated stores retain their captured image configuration until an explicit operator-reviewed upgrade. Embedded chart files are included in the runtime fingerprint. k3s uses the same charts with domain, storage, image and resource values; actual VPS/TLS verification remains later.

Open `/stores` in Relay. Active team members can create stores; the owner or team admin can retry, verify/repair and delete. Search the store rail, select a store, then inspect Infrastructure, Lifecycle, MCP tools or Operation log. Health comes from actual Kubernetes resources; CPU/memory come from Metrics API samples and can be unavailable. Allocated PVC size is not measured disk usage. Gateway state is sampled discovery, with its own timestamp. Only permission-visible tools are returned. The provisioner is a private service with tenant-bound, internal-authenticated observation; browsers never receive Kubernetes credentials or raw Secrets.

Creation reserves a per-user slot across teams in one SQL transaction. The default is two active/failed/deleting stores, a ten-minute deadline and global queue concurrency two. Idempotency IDs are bound to the actor/team/intent; a failed response can be retried with the same ID. The queue is a delivery mechanism; PostgreSQL desired state/outbox repairs lost Redis work. Status includes Provisioning, Ready, Failed, Deleting, Deleted and RecoveryRequired. No percentage is estimated. Historical attempts expose only timestamps actually recorded; completion can imply earlier verified gates without inventing missing timestamps.

Every store has a deterministic namespace, store/store-mcp Helm releases, private WordPress/MariaDB/adapter, independent PVCs and generated Secrets, a quota, LimitRange and deny-default NetworkPolicies. Gateway aliases are `store_<full immutable store UUID without hyphens>_<tool name>`; titles/descriptions carry readable store names. API management refuses to edit/remove these connections around the lifecycle, while normal enable/disable remains supported. Store-specific REST credentials remain adapter-only except the reviewed bootstrap Job. Administration is available at `<store URL>/wp-admin/`; an authorized local operator retrieves the `store-admin` Secret privately, never through a dashboard response or printed diagnostic.

A retry reuses owned resources and credentials. Missing persisted credentials, foreign ownership or changed namespace UID require operator review; never generate a replacement database identity or take over a resource blindly. Helm pending revisions may be repaired only under the per-store SQL lock after release ownership is checked. Four reconciliation attempts use bounded backoff. A deadline produces an explicit Failed/RecoveryRequired status. Component details show actual images, readiness, limits and safe diagnostic reasons. Operator logs remain private; never paste raw Secret/Helm/kubeconfig output into public evidence.

Deletion requires typing the exact store name. Routing is denied transactionally before cleanup; bounded calls drain, Helm uninstalls workloads, the namespace/PVCs/Secrets are removed and Delete-policy PVs are checked absent. Only then is the credential slot removed and Deleted recorded. Quota slots are released only at Deleted. Unknown finalizers are never stripped. A stalled finalizer or retained volume must stay visible as incomplete cleanup. On local-path storage, acceptance separately checks the recorded data directory is gone; other storage drivers need their own deletion/retention proof.

Acceptance is split into resumable scripts under `scripts/stores-*.mjs`; execute through `node scripts/run-acceptance.mjs scripts/<test>.mjs` to keep raw failure diagnostics private. `stores-recovery` intentionally kills the owned worker and loses only the validated `relay-m5` database1 queue; gateway database0 is preserved. Its checkpoint trigger is a temporary operator failure-injection fixture, removed in finally. `stores-failures` changes only identified synthetic-store resources and restores Secret/config/permissions in finally. `stores-delete` adds and later removes exactly its own test finalizer, never an unknown production finalizer. Read evidence and current SQL/Kubernetes state before resuming a failed test.
