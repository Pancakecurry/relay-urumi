# M2 observed failures and repairs

- Initial strict compilation caught an inferred pagination-loop variable and later SDK structuredContent's deliberately broad type. Added an explicit response type and parsed the fault error with Zod; strict mode was retained.
- Test-only order creation with the restricted adapter returned real Woo 403/woocommerce_rest_cannot_create. Verified the existing dedicated service identity and read_write REST permission: the role deliberately lacks publish_shop_orders. Preserved that boundary. Seeded clearly labelled orders through operator Woo CRUD in WordPress; all five required MCP operations remain REST-based. No administrator role was granted to the adapter.
- Forged-Host probe using Node fetch returned MCP 400 rather than expected Host rejection because that transport did not preserve the supplied Host (the same M1 behavior). Switched this raw security probe to Node HTTP and obtained actual 403, while retaining official SDK transport for MCP calls.
- The first complete tool run failed the midnight assertion. Real raw REST comparisons proved Woo 11.2.1 HPOS's Z-suffixed GMT filters excluded start midnight and included next midnight. Encoding timezone-less GMT strings with dates_are_gmt=true plus a one-second exclusive lower adjustment fixed both bounds. Exact UTC tool input/output remains unchanged; see date-filter-spike.json and final acceptance.json.
- The first live fault test expected timeout but K3s NetworkPolicy actively rejected the denied connection with UPSTREAM_UNAVAILABLE. Restored and compared the production policy in finally. Revised the test to preserve that truthful result and separately run the identical adapter image in a short-lived fault pod pointed to an inspected unused local pod-subnet address with a 500ms deadline. This tests actual deployed MCP/HTTP timeout/cancellation without inventing successful Woo data or changing the production store URL.
- Concurrent owned image imports emitted a transient k3d tools-container removal-already-in-progress warning. Both imports succeeded, the tools container was automatically removed, and actual runtime IDs/health were verified. Subsequent cluster imports were performed sequentially; no manual/unrelated resource cleanup.

Failed captures retain sanitized diagnostic information only. Final passed captures supersede earlier attempts; failures are not presented as acceptance success.
