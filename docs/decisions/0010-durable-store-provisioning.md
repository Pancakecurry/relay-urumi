# ADR 0010 — Durable isolated stores

Status: implemented and tested locally. Full lifecycle/fault/UI/core evidence is in `docs/evidence/m5.md`; source reproduction and final Git checkpoint are recorded separately.

PostgreSQL desired state is authoritative. A session-derived active member can create stores; the owner or team admin can reconcile, retry or delete. An admission function locks the owner across teams, reserves by counting all non-Deleted stores, checks idempotency intent and atomically inserts operations/outbox. A failed or deleting store still consumes a slot until cleanup is verified. Default limit two, ten-minute operation deadline; environment values override these guardrails.

BullMQ 6.3.12 dispatches bounded work with ioredis6.0.0. Redis database1 and `relay-m5` prefix separate queue keys from gateway admission on database0; the existing AOF/noeviction instance suffices locally. SQL scanning republishes desired state even after dispatched outbox/queue loss. At most two workers run per process. A PostgreSQL session advisory lock and renewable SQL lease protect each store across worker processes/restarts. Generation checks fence deletion/retry races. Four attempts with bounded backoff apply only to repeatable reconciliation; timeouts become Failed or RecoveryRequired, never an indefinite success spinner.

Each deterministic UUID namespace gets its quota, limit range and deny policy before workloads. Secrets are generated once in Kubernetes and never placed in Helm values, SQL, browser responses or logs. Persisted stores with a missing Secret fail for operator recovery; the worker never silently rotates database/admin/OAuth identities. Helm v4.3.0 is SHA256-verified for arm64/amd64. Existing store and handwritten adapter charts run unchanged business logic with per-store host/Secret/storage/resource values. The embedded charts are included in the runtime image fingerprint.

The controller starts with namespace get/create/delete, PV get, and permission to bind one fixed store workload ClusterRole. It receives that role only inside a managed namespace. Admission policies deny namespace mutation outside the generated managed name boundary and role bindings outside owned stores. It cannot read model/core database/original-store Secrets, exec into pods, bind cluster-admin, delete PVs or create ClusterRoleBindings. One namespaced fixed-secret Role permits updating the gateway credential vault. SQL rights exclude identity/key tables, immutable store identity fields and original upstreams. Admission policies require Kubernetes support and must be installed by the operator before enabling provisioning. The controller remains a trusted privileged component, not an untrusted image runner.

Registration follows actual SDK discovery and persists atomically with Ready. A generated store tool alias is `store_<full immutable UUID without hyphens>_<tool name>`; it remains stable across retries/renames and includes the full store identity. The readable title/description carries the store name. Existing core aliases remain unchanged. Managed URLs/credentials/removal cannot be edited around the lifecycle; normal enable/disable remains supported. Health checks sample real workloads; unhealthy existing workloads can enter a new bounded repair generation. Missing or replaced namespace identity needs operator review, rather than recreating lost data.

Deletion denies new routes in the same transaction as desired-state change, waits for bounded existing calls, uninstalls both Helm releases, deletes the namespace including retained PVCs, checks every recorded Delete-policy PV is absent, then removes the vault slot and marks Deleted. Namespace UID checks prevent deleting a replaced resource. Partial-install PVCs are inventoried before deletion too. No finalizer is stripped by production code. The acceptance suite introduces and explicitly removes only its own documented fault finalizer. Physical local-path data removal is separately verified by the operator test; PV absence alone is not misrepresented as an arbitrary storage provider's secure erasure guarantee.

Local cluster limit is4GiB inside a7.65GiB Docker VM on a16GiB host. This does not establish cloud capacity or HA. Internal HTTP remains restricted and unencrypted; public TLS, backups/restore, retention, autoscaling and the complete security roadmap remain later milestones.
