# ADR 0006 — A reproducible single-store foundation

Status: locally tested, October 10, 2026; acceptance is recorded in `../evidence/m1.md`.

Use an owned `relay-store-m1` namespace in the existing local cluster. A dedicated MariaDB 11.8 LTS StatefulSet and a single WordPress Apache Deployment use separate RWO PVCs. `Recreate` avoids pretending this single-writer filesystem supports horizontal scaling. PVCs have Helm keep annotations; uninstall is not data deletion. Local-path is node-local storage, not HA or a backup.

Build from digest-pinned official WordPress 7.1.3/PHP 8.3 and WP-CLI 2.12.0 images. Bake checksum-verified WooCommerce 11.2.1 into the image. The reviewed post-install/post-upgrade Helm Job installs WordPress only when absent, activates WooCommerce, configures URLs/permalinks/timezone/INR, classic cart/checkout and COD, and creates synthetic products by stable SKU. Existing products/orders are preserved. Admin install uses a Secret file read inside PHP, never a password argument or interactive prompt. Interrupted Helm releases must finish/repair their failed operation before rerunning; concurrent bootstrap is unsupported.

Generate private credentials once before Helm deployment. Reuse the local mode-0600 backup and owned Kubernetes Secrets, refusing rotation on missing backups or conflicts. The stable pre-generated WooCommerce consumer key lets a restarted Job look up its database hash instead of generating duplicate keys. Key storage follows the pinned WooCommerce creation implementation (`wc_api_hash`, secret, permission, truncated key); this intentional schema-coupled bootstrap needs review on plugin upgrades. Business order/product integrations use REST, never order tables. Bootstrap is an installation boundary, not the future adapter.

WordPress runtime receives only DB password and persistent signing salts. MariaDB receives only its DB/root passwords. Admin and REST credentials are mounted only into the installation Job; the future private adapter will mount `store-adapter`. No pod gets a Kubernetes service-account token. Cluster administrators still have Secret access. Application network policy permits Traefik→WordPress and WordPress/bootstrap→own DB; DNS is allowed, arbitrary outbound telemetry/update/mail traffic is not. No public DB Service or Ingress exists.

The upstream Apache entrypoint starts as root to copy/chown persistent files and bind port 80, then request workers run as www-data. The MariaDB entrypoint also starts as root for volume permissions, then drops to mysql. Bootstrap WP-CLI runs as root to initialize the shared volume. This chart does **not** claim restricted-policy/non-root compatibility. RuntimeDefault seccomp and no service-account token apply; root init and writable roots remain documented constraints. A non-root redesign requires an actual separate compatibility gate, not an untested runAsUser override.

Local URLs use the existing loopback-only port 18080 with a hostname-based Ingress. Chrome resolves `.localhost`; command-line tests use 127.0.0.1 transport with the canonical Host. HTTP REST authentication uses one-legged OAuth HMAC-SHA256 in the Authorization header, avoiding URL credentials. Production values specify HTTPS/TLS and a registry image digest; no registry or VPS is provisioned. OAuth signatures authenticate requests; HTTP provides no confidentiality, and WooCommerce OAuth does not sign request bodies. Production and any non-loopback transport require TLS.

Automatic updates are disabled to preserve reviewed versions; pin updates must be rebuilt and tested. Persistent WordPress core files do not automatically upgrade just because the image changes; future upgrades need explicit core/plugin migration and recovery procedures. Synthetic products are virtual so COD checkout needs no shipping service. No real payments, delivery, SMTP or external integrations are claimed.

References: [official WordPress packaging](https://hub.docker.com/_/wordpress), [MariaDB health checks](https://mariadb.com/docs/server/server-management/automated-mariadb-deployment-and-administration/docker-and-mariadb/using-healthcheck-sh), [WooCommerce authentication](https://developer.woocommerce.com/docs/apis/rest-api/authentication), [pinned credential creation code](https://github.com/woocommerce/woocommerce/blob/11.2.1/plugins/woocommerce/includes/class-wc-auth.php), [COD configuration](https://woocommerce.com/document/cash-on-delivery/), [WP-CLI core install](https://developer.wordpress.org/cli/commands/core/install/).

Observed bootstrap defect: WP-CLI `--prompt` echoed the initial password into its output. Replaced with `eval-file --skip-wordpress` and a PHP installer reading the mounted file, rotated the affected admin password and removed the old hook/capture before staging. A genuinely empty second store install verified the replacement procedure. The final evidence/log/index scans check current credentials. This repair is part of M1, not a claim that the rejected procedure was safe.
