# ADR 0008 — Durable identity and the private MCP gateway

Status: implemented for M3; acceptance evidence is in `docs/evidence/m3.md`.

Keep separate API and gateway processes. The API handles Better Auth browser sessions, team management and a narrowly privileged Secret-management module. The gateway is the only application process that connects to the private upstreams. PostgreSQL is identity/registry/audit authority; Redis provides shared request windows and concurrency leases. BullMQ/outbox provisioning remains M5, full external OAuth M6, and dashboard/model chat M4. These assignments follow the full plan rather than treating those features as deleted.

## Durable identity and tenancy

Better Auth 1.7.7 uses its Drizzle adapter and explicit `auth` schema definitions. Its supported password mechanism owns password hashes, cookies and session rows. Cookie caching is disabled. Local cookies are HttpOnly/SameSite=Lax; production HTTPS enables Secure. Same-origin management writes require the exact Origin, and auth routes also use the library's CSRF/Origin checks. The HTTP auth wrapper strips bearer session tokens from JSON responses while preserving Set-Cookie. Public email verification/SMTP is future production work; the current loopback demonstration uses synthetic accounts and manual invitations.

The migration/operator, identity and application roles are distinct. Runtime roles are neither owners, superusers nor BYPASSRLS. Application team tables have RLS and each transaction sets tenant context with transaction-local `set_config`; no context survives pool reuse. Narrow SECURITY DEFINER functions reveal session validity, identity existence and the logged-in user's team list. They have a fixed search path and no PUBLIC execution. The application role cannot read auth password or session-token tables. RLS prevents omitted tenant predicates, not compromise of the trusted application process.

Personal keys contain a public team UUID and lookup UUID plus 256 random bits. Store SHA-256 of the whole token, reveal it once, retain revocation and last-use metadata, and compare digests in constant time. This is high-entropy token hashing, not password hashing. Every MCP HTTP request and pre-execution callback reads current membership/key/session state. No MCP session substitutes for authentication. Invitations use the same high-entropy/hash approach, an email/role/team binding, a 24-hour expiry and row locking. Repeating acceptance by the same identity is idempotent; it creates no second membership or role change. The last active team admin cannot be removed or demoted.

Chat delegation is a platform-internal HMAC credential, not an ad hoc OAuth token server. A trusted API endpoint derives user/team/session from a real browser session. It signs issuer, audience, issued/expiry times, session ID and nonce, for at most 60 seconds. The gateway verifies the signature/claims and live session/membership. The public Ingress exposes `/api` and `/mcp`, never `/internal`. Full MCP OAuth discovery, PKCE, consent and external callback acceptance remain D03/M6.

## Registry, secrets and destinations

Registry UUIDs are immutable; PATCH requires a current revision. Disable/removal first denies routing in PostgreSQL. Removed registrations remain tombstones so historical audits survive. Admin views show URLs and credential presence, not values. Member views cannot read the registry credential settings.

The API's Secret manager can GET/UPDATE exactly `relay-platform/gateway-upstream-credentials`. It cannot list/create Secrets, read database/admin Secrets or access store adapter credentials. That fixed Secret holds team-bound opaque credential references. Credential edits are write-only. Kubernetes encryption at rest is already enabled by the dedicated k3s setup. Secrets stay outside Helm values/history. The gateway has no service-account token and retrieves only the selected registration's headers through a guarded internal API call. Neither process mounts WooCommerce REST/admin/DB credentials. Kubernetes Secret and SQL updates are not one distributed transaction: a crash can leave an unused credential slot requiring operator cleanup; routes remain governed by durable SQL state. Full Secret lifecycle/rotation/reconciliation remains M6.

Reviewed private endpoints are HTTP port 3000 `/mcp` Service DNS in the two owned upstream/store namespaces. Additional external HTTPS endpoints require operator allowlisting. All DNS answers are validated and the connection is bound to a validated IP; redirects are refused. Private Service IPs must be in the local k3s 10.43/16 range. External non-public and IPv6 addresses are denied conservatively. Other Service CIDRs, generated store namespaces, external IPv6 and broader connector lifecycle need the planned M5/M6 integration; no broad allow-all escape exists. Local internal HTTP is restricted but unencrypted.

## MCP and failure handling

Use official MCP SDK v2 server/client 2.3.1, the Fastify integration and Node adapter. A fresh authenticated server factory exposes the current allowed catalog for each request. SDK-owned Streamable HTTP handles modern 2026-07-28 and legacy 2025-11-25. Rejection tools also go through the SDK: hand-constructing a legacy-shaped result omitted modern `resultType` and failed real interoperability testing. We corrected that rather than weakening protocol validation.

An alias is `t_` plus base64url SHA-256 of `immutable upstream ID + NUL + original name`: 45 characters. The route map, not label splitting, identifies the destination. Renaming a display label does not change its aliases. Per-upstream schema/status snapshots persist at the current registry revision; changed schemas refresh on discovery. The cache is not an immutable archive of every schema refresh. The SDK defaults tools.listChanged to true when tools are registered; the gateway explicitly disables that capability because this stateless deployment uses client refresh/reconnect. Inspector verifies the advertisement. Status polls every five seconds for teams seen by that gateway process, and first access refreshes missing/stale snapshots. This is lazy team activation, not an already-built global background registry reconciler. Disabled/removed/currently denied routes are filtered and reauthorized; stale aliases cannot bypass a new policy.

Discovery has three-server bounded fanout and a 2-second connection/discovery deadline. Normal tool connections/calls share a configurable deadline up to 10 seconds. A failed server retains its last known schemas at the same revision and gets Unreachable status, while healthy servers remain available. Database/Redis readiness is independent of upstream health. Calls use fresh server-owned headers and fresh official SDK connections; no ambiguous mutation is automatically retried. Input/output are bounded; schemas reject remote references, excess size/depth and unreviewed patterns. A Standard Schema bridge preserves the reviewed JSON schema and validates it with Ajv 2020. Semantic refinements that JSON Schema cannot express are still enforced by the handwritten upstream.

Redis windows are 120 requests/key-or-session and 240/user per minute. Concurrency leases bound one upstream to 4, a team to 8 and the gateway pool to 16. These are admission limits, not an HA guarantee; multiple-replica acceptance remains D07. Redis is authenticated, persistent AOF and non-evicting. A 12-second lease exceeds the maximum tool budget; crashed processes release capacity by expiry.

## Audit and interrupted requests

Persist audit-start before dispatch. Store actor, key/delegation kind, upstream/original name/alias, UTC timestamps, duration, status/code and an argument hash; raw arguments/results/customer data/credentials are excluded. Complete the audit before returning a normal tool result, and return a safe audit correlation ID. Retained revoked keys attribute valid-but-revoked attempts; random credentials create anonymous security events. Members see their own calls; admins see their team only.

A disconnect signal is combined with the SDK's signal and propagated to the upstream. The Node adapter may return on disconnect before the tool callback settles; one shared finalization promise avoids competing updates and labels cancellation accurately. Unfinished starts older than 30 seconds are marked unknown/GATEWAY_INTERRUPTED when that team next uses the gateway; they are never replayed. Audit admission failure prevents tool side effects. If PostgreSQL itself is unavailable, persistence of that rejection is also unavailable; the gateway fails closed rather than claiming an audit record exists. Boundary/parser rejection auditing is handled separately; a body rejected before parsing cannot provide a trustworthy tool name.
