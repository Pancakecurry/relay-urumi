# 0007 — Three private Streamable HTTP upstreams (M2)

Date: 2026-10-10. Baseline: official employer brief, full-scope plan W01–W04/G06 and M2. Accepted implementation; execution evidence is recorded separately in `docs/evidence/m2.md`.

Use the already tested SDK v2 packages (server/client 2.3.1, Fastify adapter 2.0.1, Node adapter 2.1.1). Read their installed declarations and official v2 documentation, including `ctx.mcpReq.signal`; do not mix v1's callback API. The SDK owns protocol negotiation and wire encoding. Each HTTP request has a fresh McpServer, no durable MCP session identity. Separate deployments/processes expose `/mcp` via ClusterIP only. Readiness verifies server configuration/transport availability, not the store's availability; a store outage returns an explicit tool error and does not make utilities unavailable.

The handwritten Woo adapter uses REST v3, not SQL or a third-party MCP plugin. It runs beside its one store, mounts only Woo REST credentials plus its own upstream bearer credential, and can egress only DNS and that store's WordPress pod. Utility deployments have separate bearer Secrets and DNS-only egress. Namespace+pod label selectors permit only `relay-platform` pods with `relay.role=gateway` to enter upstreams. Kubernetes operators remain privileged: labels are not user authentication, and exec/port-forward bypasses this boundary. The M2 acceptance client is an explicitly privileged, temporary gateway-labelled fixture, not the M3 authenticated gateway. Browser and external product clients will connect only to the M3 gateway.

Local store HTTP requests use Woo's OAuth HMAC-SHA256 header signing with per-request nonce/timestamp. Sign the canonical public origin and send its Host header while connecting directly to WordPress Service DNS; no credential in URL, query, command line or log. HTTPS configuration uses Basic authentication over CA-verified TLS, with no downgrade or redirect following; this branch still needs a deployed TLS endpoint acceptance. Plain cluster HTTP does not encrypt bearer credentials or store traffic. NetworkPolicy and encrypted-at-rest Secrets reduce exposure but do not replace transport encryption. Public/VPS TLS and internal encryption remain tracked security/deployment work, not silently completed.

Tool inputs are strict, bounded Zod objects; output schemas are published and parsed before returning text plus structured content. Unknown fields are rejected. Product creation requires a SKU, defaults to a simple published/visible product, and accepts a decimal string in the configured store currency. Orders deliberately omit customer addresses/email/phone, keys and arbitrary metadata. Statuses are the standard seven Woo values; custom plugin statuses are not currently supported. Duplicate SKU rejection is propagated, not converted to a false success or silent upsert.

Pagination is one explicit page (1–100 items) with validated Woo `X-WP-Total`/`X-WP-TotalPages`, `next_page`, stable ID ordering. An empty or short page is not reported as all store data. Date bounds are validated UTC instants at second precision and form `[after,before)`. Woo 11.2.1's exclusive `date_query` lower bound is adjusted by one second, including the start exactly. The HPOS GMT column filter expects timezone-less date strings with dates_are_gmt=true: the actual Z-suffixed attempt shifted both bounds. Keep explicit UTC in our contract but strip Z only when encoding the REST GMT filter; date-filter-spike.json records both actual outcomes. Real orders at both boundaries are the acceptance proof; no order SQL/HPOS assumptions are substituted for that test.

Calendar uses the pinned `@js-temporal/polyfill` 0.5.1: explicit IANA timezone, valid ISO date, UTC half-open day bounds, real current time, DST 23/25-hour days and skipped-day rejection. Totals uses BigInt minor units, never floating point. Currency precision is deliberately limited to INR/USD/EUR/GBP (2), JPY (0), KWD (3); unsupported currencies/extra fractions are rejected. `sum_orders` rejects duplicate IDs and mixed currencies and sums only the provided pages.

REST deadlines are 8 seconds locally (configurable 100–10000 ms), response limit 1 MiB, MCP body limit 256 KiB. Cancellation forwards the SDK signal to Node HTTP; errors omit raw provider messages, stack, URL and secrets. Failed reads may be marked retryable, but no automatic retry exists. Interrupted writes return `outcome=unknown` with no retry permission; reconcile SKU or get the order before deciding what to do. Business rejections remain `isError=true`. Status assignment can trigger hooks and therefore is not advertised as unconditionally idempotent.

All upstreams intentionally expose `info`. A pure M2 route-table helper uses SHA-256 of immutable upstream ID + NUL + original tool name, base64url with prefix (45 characters), and rejects duplicate/colliding routes. Calls use the saved route tuple rather than parsing an alias. The production dynamic catalog, gateway authorization and model-driven multi-server prompt remain M3/M4. M2's Calendar→Woo→Totals workflow is a real SDK acceptance sequence, not autonomous LLM evidence.

A shared runtime image contains all three programs, but each deployment starts exactly one. Third-party dependencies are declared in the runtime packaging manifest and root compilation environment; owned code imports relative compiled modules. Root TypeScript emits the same tree in development/container, avoiding node_modules TypeScript execution or unbuilt workspace exports. M0 Docker build inputs now include initialized workspace packages so the frozen graph remains buildable; its behavior remains ping only. No queues, database, gateway abstractions or model packages are added prematurely.
