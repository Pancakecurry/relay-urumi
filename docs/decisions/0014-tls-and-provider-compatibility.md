# ADR0014 — verified local TLS and exact-version compatibility bridges

Status: accepted for the verified local M6 release on October 22. Earlier spike/failure notes below are retained as implementation history; current acceptance is summarized at the end.

The official MCP Fastify2.0.1 factory does not expose HTTPS/serverFactory options. Its exported host/origin guards and the official MCP Node handler are therefore composed on Fastify5.12.5 with a native HTTPS server factory. No MCP generation, handshake, transport or tool implementation changes. Both modern and legacy official clients already called real ping over CA-verified TLS1.3 in an isolated Kubernetes workload.

The signed cert-manager1.21.2 chart and all four deployed component image indexes are pinned. A real CA/leaf issuance and changed-spec reissuance passed on k3s1.37.1. Its published tested matrix ends at1.36: this is observed local compatibility, not vendor-listed support. The upstream chart's `v1.21.2` version also produces a Helm SemVer warning; lint succeeds without suppressing it. It remains a separate release, with measured limits, not a platform subchart. No ACME/cloud account or OS trust root is installed.

Node services load a consistent projected key/certificate generation and reload server contexts on renewal. New TLS handshakes must see the new certificate; an existing TLS socket correctly retains its original handshake identity. The compatibility test was repaired to open a fresh connection for that assertion. Trusted internal callers additionally present a CA-verified service certificate and an exact service CN for private API paths. Bearer tokens remain required. Traefik verifies backend SAN/CA and presents its own service identity. Local external clients explicitly load the project CA; scoped browser-test certificate pins are documented separately. Global certificate checks are never disabled.

Better Auth OAuth Provider1.7.7's emitted TypeScript declarations conflict with this repository's `exactOptionalPropertyTypes` in generated OpenAPI metadata and plugin hook context generics. A narrow plugin ABI bridge preserves the native endpoint key map (rather than adding an arbitrary endpoint index), metadata and runtime hooks, and bridges the native server-only endpoint context to the provider's published capability type. This does not convert token payloads to trusted identities: their issuer, resource, session, client, scope, expiry and team membership are validated at runtime. Strict/exact compiler settings and all tests remain enabled. Real OAuth acceptance is mandatory before accepting this bridge as interoperable.

These local controls do not complete D01 public hosting/TLS or the full D06 fleet, Secret, SSRF and runtime security matrix. Root CA rotation requires a reviewed overlapping trust distribution; leaf hot reload alone is not a root-rotation claim.

WordPress/MariaDB migration is being isolated before changing any retained store. The running image uses WordPress7.1.3 and mysqlnd8.3.35. Inspection confirmed wpdb initializes mysqli without an ssl_set hook; mysqlnd's source defaults to no peer verification when no SSL options are supplied. TLS flags alone are insufficient. The proposed image therefore adds a small, explicitly named TLS bridge at the single mysqli_init anchor, guarded by the exact unmodified wpdb SHA256. It refuses unknown/core-edited files, retains permissions and replaces only the reviewed driver file atomically; WooCommerce data/configuration/uploads are retained. The bridge calls native mysqli_ssl_set with the mounted CA/client identity and explicitly requires server verification. This creates an intentional core-checksum difference, so a WordPress version update must review the bridge and hash again. No such version upgrade is automatic. The rootless Apache listener uses8080/8443 with explicit writable runtime mounts; actual fresh/PVC/TLS/negative verification remains open.

The isolated TLS store initially failed closed because mysqlnd8.3.35 returns false for mysqli_options(MYSQLI_OPT_SSL_VERIFY_SERVER_CERT,true). Real native connections with the CA rejected both wrong CA and wrong hostname, and the installed driver exposes MYSQLI_CLIENT_SSL_VERIFY_SERVER_CERT. BridgeV2 therefore sets that explicit native connection flag with MYSQLI_CLIENT_SSL and supplies ssl_set CA/client material. Original/V1/V2 full-file hashes are checked, including idempotent target reads; no unknown-marker shortcut remains. WordPress, MariaDB, bootstrap and the private MCP adapter now reach Ready in the isolated clean-store Helm proof. Complete operations/checkout/isolation evidence still follows.

The first native data-service rollout failed closed: PostgreSQL18.6 rejected `map=` with SCRAM authentication. Its exact HBA parser permits maps only with ident/peer/gssapi/sspi/cert/oauth, so the documented generic certificate-mapping description is not a valid SCRAM combination here. Redis reached Ready with mutual TLS; PostgreSQL did not. Rolled back specifically to verified M6 revision34 (AEAD-vault-compatible image e71fb0c537c0f630), preserving the original Redis configuration and all PVCs. A bad StatefulSet revision requires replacing the failed pod after its template is reverted; no volume reset is part of that repair.

The corrected design retains `scram-sha-256 clientcert=verify-full`, with dedicated client certificates whose CN exactly equals each SQL role. API and gateway receive only the shared application role certificate; API additionally receives auth; provisioner receives its own role; migration receives postgres. The gateway never receives auth/provisioner/migration key material. Service HTTPS and Redis keep distinct service identities. Both certificate and password checks stay enabled; no CA-only/password-only workaround is being labelled final acceptance. Native data TLS remains pending real retry/negative/rotation verification.

## Final local acceptance — October 22

Fresh TLS store, native SQL/Redis authentication, rootless filesystem permissions, all five Woo tools, HTTPS COD/admin/persistence, protocol compatibility, OAuth and negative security tests pass. The current runtime is `m6-99a36532c5ab56f3`; `docs/evidence/m6/clean-install.json` verifies an independent empty-cluster installation. Native peer identities after renewal match mounted Secrets following the controlled reload in `docs/evidence/m10/identity-reload.json` and `tls-peers.json`. PHP/native SQL/Redis and long-lived clients still require controlled reload; automatic leaf issuance is not automatic full-fleet reload or root rotation. Publicly trusted cloud TLS remains a separate deployment gate.
