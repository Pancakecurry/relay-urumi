# ADR0013 — provider-native opaque OAuth access tokens

Status: accepted after real external-client, browser,12-group security and four-group cross-replica acceptance; full M6 fleet regression remains pending.

Use the official Better Auth OAuth Provider1.7.7 with `disableJwtPlugin: true`, hashed access/refresh token storage, authorization-code/S256 PKCE and explicit resource-bound scopes. This changes the initial M6 checklist's JWT assumption, not the accepted Better Auth identity architecture or MCP SDK generation. OAuth/MCP do not require JWT access tokens.

The installed provider's `revokeJwtAccessToken` explicitly reports `unsupported_token_type` for a live self-contained JWT; its JWT validation checks signature, client and session but does not maintain a per-access-token revocation list. Its opaque path checks a durable token hash, expiry, revocation, current client and current session on validation; access-token revocation deletes the corresponding row. That matches the required immediate revocation semantics without a separate custom JWT denylist. The provider continues to own authorization codes, PKCE, consent, refresh rotation, token validation and revocation.

Use admin-managed public clients scoped to one team through server-owned metadata. No client-secret capability, machine grant, open registration or user-controlled private metadata is enabled. A current active membership and the same application permission evaluator remain mandatory on discovery and every call. Tokens must target the exact gateway resource and required scope. No raw access token is persisted in application tables, returned in management APIs or emitted in evidence.

TLS, real browser consent, external official-client interoperability and negative expiry/revocation tests remain required before D03 is complete. No token is minted through a custom signing shortcut or provider raw issue primitive.

The installed provider applies its client privilege hook even to server-only administrative endpoints. Relay therefore enters an AsyncLocalStorage scope only after a current session/admin check under the team lock. The provider's privilege hook requires that server scope, matching user and team header, and the create/update action. Its clientReference uses the same scope to give the team ownership without mutating a session's active-team field. Direct HTTP callers cannot create this server capability. This replaces the initial blanket-false privilege callback, which correctly denied the first real registration attempt. Machine-scope/resource management remain denied.

Provider private metadata is serialized by its own persistence layer. The application accepts both native JSON objects and the provider's JSON string representation when filtering team ownership; callers cannot supply either private representation through Relay's strict client-management contract.

The actual external official client completed metadata discovery → S256 browser login/consent → code exchange →12-tool discovery → real Calendar execution and correctly attributed audit (`oauth-client.json`). Client-resource links are created by the native `clientRegistrationDefaultResources` setting with per-client resource enforcement retained. Consent uses the native HTTP handler with a real Request after Relay validates the signed query/team/session; calling the provider's server method alone loses its authorization continuation context.

Negative testing found a real installed-version discrepancy: although current documentation describes `adminUpdateOAuthClient({update:{disabled}})`,1.7.7's actual endpoint Zod schema omits disabled and strips it silently. The first disable acceptance correctly failed (the token still worked). Migration0008 adds a narrow SECURITY DEFINER capability to update only the provider's declared native disabled field, checking the current transaction tenant and live administrator. It commits with the management audit event. Native token validation, issue and introspection continue to check that field; no token semantics or provider internals are replaced. Earlier synthetic clients were repaired under an exact synthetic-team/name guard; stored disabled state is now checked during cleanup instead of trusting a response echo. Never describe that earlier failed test as a pass.

The pinned provider also documents a multi-step refresh-family invalidation race. A bounded, separate two-connection PostgreSQL advisory-lock pool serializes the native token/revoke handlers per public client across API replicas. Busy contenders release connections between attempts and fail closed after three seconds. The provider still performs every code/PKCE/issue/refresh/revoke operation. Hash collisions can only serialize unrelated clients. A real concurrent acceptance remains required before the guard is considered verified.

Final external client acceptance also rejects wrong state at the real loopback callback and wrong/missing issuer through the official SDK before code redemption. Production300-second expiry passed without clock/row changes. Concurrent refresh, code replay and refresh/revoke on two actual API pods leave no stored/usable family tokens; a real held DB lock returns503 in3021ms. API replicas and synthetic clients were restored/disabled with durable-state checks. Evidence: oauth-client.json, oauth-security.json and oauth-concurrency.json. No model calls.


Final cross-replica testing found a pinned-provider HTTP compatibility defect: Better Auth OAuth Provider1.7.7 invalidates a rotated/revoked refresh-token family, then returns400 invalid_request because its APIError name comparison does not match the emitted exception. The failed diagnostic is preserved in oauth-revocation-spike.json; no usable family rows/tokens remain. RFC7009 section2.2 requires200 for an invalid token (https://www.rfc-editor.org/rfc/rfc7009#section-2.2). A narrow post-handler compatibility function normalizes only the four exact native invalid-token descriptions to an empty200 on POST oauth2/revoke. Native client validation, locks, token state changes, malformed requests, unsupported token types and all other errors remain intact. Focused tests assert these boundaries; final actual concurrency/repeated-revocation acceptance remains required after deployment.
