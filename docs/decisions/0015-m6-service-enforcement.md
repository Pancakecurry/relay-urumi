# ADR0015 — durable management and authenticated store transport

Status: implemented; final M6 gate remains open until all live regression evidence passes.

All management mutations serialize on the tenant row and resolve current membership/session after acquiring that lock. Issuing another person's key requires the current administrator role. This closes queued-request escalation after a role change; the operator-controlled race test actually holds the same lock, demotes the requester, and verifies rejection of invitations, member promotion, registry creation and other-user key issuance. No production fault endpoint is introduced.

A credentialed upstream URL change requires explicit fresh credentials or explicit clearing. Credentials remain write-only, encrypted and revision-bound; the old reference cannot be paired with an edited destination accidentally. The three original core upstreams were upgraded by a reviewed operator migration that checked the unchanged Service authorities and issued certificates before changing registry URLs. The operator migration is not a general endpoint-edit bypass.

Native PostgreSQL uses SCRAM plus a dedicated client certificate whose CN equals the requested SQL role. Redis uses native TLS with client certificates and its existing password. The original passwords and all persistent volumes are retained. The gateway lacks the auth, provisioner and migration SQL identity keys. TLS native clients load their projected identity when their pool/client starts; controlled rollout is required after renewal, distinct from Node HTTP server context reload.

New stores freeze transport version, reviewed store/adapter images, issuer, storage class and HTTPS port in durable desired state. A separately reviewed UID-checked migration updates retained Boreal desired state and reconciles through the normal outbox/worker/Helm path. Original product IDs, order count, uploaded marker and both PVC/PV identities remain unchanged. Migration0009 adds the explicit URL scheme to the store request function; readiness requires that migration. The initial missing runner registration caused real503 responses and was repaired, rather than recording those calls as successful.

The provisioner may request only its three service certificates in managed namespaces. Admission binds exact CN/SAN/Secret names, issuer, usages, key profile and lifetime to the store. Alternate CA identities, core service/SQL identities and arbitrary Secrets are prohibited. Native CertificateRequests, root/model Secrets, exec, cluster-role escalation and PV deletion remain outside its RBAC. A separate workload policy rejects root/privileged/host/token/writable-root/capability configurations before creating a workload; namespace Pod Security remains an additional boundary.

Upstream response validation runs before MCP schema decoding. JSON and complete SSE data frames reject prototype-related keys; response bytes, frame size, total duration and socket closure remain bounded. The official decoder's removal of a prototype property was observed by a real hostile-peer test; it did not count as our intended wire rejection. Upstream descriptions/results remain untrusted data: these controls do not establish arbitrary prompt-injection immunity or prevent every covert leak by a server that legitimately holds its own credential.

Local TLS uses explicit project trust. No system root, external cloud capacity, new purchase or additional model traffic is authorized by this milestone. Public VPS acceptance remains D01, and later scaling/observability/upgrade differentiators retain their original scope.


Final cross-replica testing found a pinned-provider HTTP compatibility defect: Better Auth OAuth Provider1.7.7 invalidates a rotated/revoked refresh-token family, then returns400 invalid_request because its APIError name comparison does not match the emitted exception. The failed diagnostic is preserved in oauth-revocation-spike.json; no usable family rows/tokens remain. RFC7009 section2.2 requires200 for an invalid token (https://www.rfc-editor.org/rfc/rfc7009#section-2.2). A narrow post-handler compatibility function normalizes only the four exact native invalid-token descriptions to an empty200 on POST oauth2/revoke. Native client validation, locks, token state changes, malformed requests, unsupported token types and all other errors remain intact. Focused tests assert these boundaries; final actual concurrency/repeated-revocation acceptance remains required after deployment.
